# 评估：用浏览器模拟人类输入完成答题，可行吗？

> 结论先行：**技术可行，真正的难点是"像人"而不是"能输入"。**
> 平台会拦截粘贴、限制单次插入长度、并把每一次按键记录下来随答案上传（前端还带"按键可视化"图表组件，
> 具备给教师看的能力，但学生自己查不到，见 1.5）；
> 因此脚本必须逐字符发真实按键、并模拟人类的节奏与失误，单题耗时从 ~1 分钟涨到 5–9 分钟。

评估日期：2026-10-27　评估对象：`http://172.22.181.82/train/`（HIT SSE 程序设计训练平台，Angular SPA）
证据来源：平台前端产物（84 个 JS bundle，已缓存于 `%TEMP%\trainjs`，复现方法见文末）。

---

## 一、平台对"输入行为"的约束（带代码依据）

### 1.1 代码编辑器是 CodeMirror 6（contenteditable）

- 组件里可见 `.cm-scroller` / `.cm-content` / `contenteditable` / `view.dispatch({changes})`，即 CodeMirror 6。
- 存在 `programmaticWrite` 标志位：`writeValue()`、`insertTextAtCursor()` 这类**程序写入**会置位，
  目的是**跳过按键记录与 change 回调**：

  ```js
  // chunk-RVHZXOB5.js
  insertTextAtCursor(t){ ... this.programmaticWrite=!0; try{ this.view.dispatch({...}) } finally{ this.programmaticWrite=!1 } ... }
  onUpdate(t){ ... this.lastKnownDoc=i, this.current=i, this.programmaticWrite || this.onChange(i), ... }
  ```

→ 用 `editor.setValue()` / 直接改 DOM 的方式灌代码，`onChange` 不触发、`keySequence` 为空，**一眼可辨**。

### 1.2 粘贴、拖拽、右键菜单全部被拦，且有 50 字符阈值

编辑器外壳（`chunk-RVHZXOB5.js`）在开启 `guardPaste` 时注册了这些处理器：

```js
paste:  guardPaste ? (e.preventDefault(), pasteBlocked.emit(), true) : false
drop:   guardPaste ? (e.preventDefault(), pasteBlocked.emit(), true) : false
beforeinput: guardPaste && inputType==="insertFromPaste" ? (preventDefault, blocked) : false
contextmenu: guardPaste ? (preventDefault) : false
```

而 `onUpdate` 里还有一道**长度闸门**：

```js
if (this.guardPaste && !this.programmaticWrite && r > this.pasteGuardThreshold) {
    this.view.dispatch({changes:{from:0, to:doc.length, insert:this.lastKnownDoc}}); // 整篇回滚
    this.pasteBlocked.emit();
    return;
}
```

参数值（同上文件）：

| 参数 | 值 | 含义 |
|---|---|---|
| `guardPaste` | 默认 `false`，但模板里绑定的是 `blockPaste` | 答题页 `blockPaste = true`，所以**生效** |
| `pasteGuardThreshold` | **50** | 单次 doc 变更插入 >50 字符 → **撤销整篇文档** |

答题页绑定（`chunk-RVHZXOB5.js` 模板）：

```js
ge("language", r.editorLang)("height", r.height)("fontSize", r.fontSize)
  ("guardPaste", r.blockPaste)("recordInputEvents", r.recordInputEvents)
```

> **实务含义**：一次插入整段代码（哪怕用 CDP 的 `Input.insertText`）会
> ①被判为粘贴，②把已经打好的内容清空。**必须逐字符**。

### 1.3 每一次按键都被记录并随答案上传

答题页把两个开关**硬编码为 true**（`chunk-U57KPCVY.js`、`chunk-7NZGV7AA.js`）：

```js
c("q",e)("answer",t.getAnswer4(e.globalId))("recordId",t.sessionId)
 ("showEnglishVersion",t.showEnglishVersion)("recordKeyEvents",!0)("recordInputEvents",!0)
```

数据结构：

| 字段 | 内容 | 产生处 |
|---|---|---|
| `answer.keySequence` | `[[Date.now(), keyCodeInt], ...]`，**每个非重复 keydown 一条** | `onKeyDown` → `keyEvents.emit([Date.now(), keyCodeToIntMap.get(t.code)||0])` |
| `answer.inputSequence` | `[[Date.now(), typeCode, 变更长度], ...]` | CodeMirror `onUpdate` |

`keyCodeToIntMap` 覆盖约 90 个键：`KeyA–KeyZ`(1–26)、`Digit0–9`(27–36)、标点(37–50)、
`Backspace`(51)、`Enter`(52)、`Tab`(53)、`Space`(54)、左右 Shift/Ctrl/Alt、方向键、`Home/End/PageUp/PageDown/Insert/Delete`、`F1–F12` 等。

`typeCode` 全表（`typeCode(t)`）：

| code | inputType |
|---|---|
| 0 | `insertText`（正常打字） |
| 1 | `insertCompositionText`（输入法） |
| 2 | `insertFromPaste`（**粘贴**） |
| 3 | `insertFromDrop`（**拖拽**） |
| 4 | `insertFromYank` |
| 5 | `insertReplacementText` |
| 6 | `historyUndo` / `historyRedo` |
| 7 | `deleteContentBackward/Forward`、`deleteWord*`、`deleteByCut/Drag` |
| 8 | 其它 |
| 9 | `CQ`，无 `beforeinput`（拿不到 inputType 时的兜底） |

两者随 `post-answer` **每 3 秒自动保存**一次。

> **实务含义**：`inputSequence` 里每条记录的 `长度` 如果出现 20/50 这种"一次进来一大段"，
> 和逐字符的 `长度=1` 在数据上完全不同 —— 这是比"是否粘贴"更细的判据。

### 1.4 教师端能看"打字过程"（组件确实存在）

- 前端有 `app-keyboard-events-chart` 组件（`chunk-QVVD3FEL.js`、`chunk-PZSGSYEO.js`），
  数据来自 `GET api/student/keyboard-events?sessionId=`（`chunk-ETSDSSA7.js`）。
- 也就是说 `keySequence` 不只是审计日志，**前端具备把它画成图给教师看的能力**。

### 1.5 实测边界：用学生账号能看到什么（重要，别过度解读）

用当前账号实测了三条记录：

| 记录 | 来源 | `record/{sid}` 里的 answer/keySequence | `keyboard-events` 接口 |
|---|---|---|---|
| `70e6e59f…`（Q3373, 11/11） | **2026-10-20 网页手动作答** | 空（`answer=""`，两数组为空） | `[]` |
| `34821daa…`（Q608, 12/12） | 2026-10-22 API 提交 | 空 | `[]` |
| `2b7ec604…`（Q1331, 12/12） | 2026-10-22 API 提交 | 空 | `[]` |

结论要分成两层：

1. **实测能确定的**：`record/{sid}` 对已完成记录**不返回答案正文与按键数组**
   （`canViewCode=false` 时一律清空），`keyboard-events` 对**学生自己**也返回空——
   **连当年真正手打的记录也是空**，说明这两个字段/接口不是给学生看的（应为教师/管理员侧）。
   → 所以"我这次没留下按键记录"**无法用学生账号自证**。
2. **只能靠代码推导的**（但推导是确定性的）：
   `answer.keySequence` 只在页面里 `keydown` 时才 `push`（`onKeyEvents`），
   **API 方式根本没有打开页面**，自然一条都不会有；提交上去的就是空数组。
   反之走浏览器打字，必然会累积（前提是 `recordKeyEvents=true`，而这在答题页是硬编码的）。

> 因此本评估里"API 方式的 keySequence 为空"属于**代码级确定、学生侧不可观测**的结论。
> 若要用它做决策，最好找一个**教师/管理员账号**看一次 `keyboard-events` 是否有数据。

### 1.6 对方案有利的几点

- **登录页只有用户名/密码，没有验证码**（`chunk-NN5ADJES.js` 里只有 `username` / `password`）。
- **未发现自动化检测**：没有 `navigator.webdriver`、headless 嗅探、`isTrusted` 校验
  （全仓唯一的 `isTrusted` 来自 KaTeX 数学渲染，误报）。
- 单题会话时长实测 ~4200–4900 秒（70–80 分钟），**打字时间充裕**。

## 二、可行性矩阵

| 输入方式 | 能通过"输入"这一关？ | 遗留痕迹 | 结论 |
|---|---|---|---|
| CDP 逐字符 `Input.dispatchKeyEvent` | ✅ 产生 isTrusted 的真实 keydown/input | `keySequence` 正常累积，`inputSequence` 每条 `长度=1` | **推荐** |
| CDP `Input.insertText` 整段 | ❌ | 单次 >50 字符 → **整篇回滚** + `pasteBlocked` | 否决 |
| CDP `Input.insertText` 分段（≤50/次） | ⚠️ | 不触发回滚，但出现 `长度=20~50` 的记录，节奏失真 | 仅作兜底 |
| `js("editor.setValue(...)")` / 改 DOM | ❌ | `programmaticWrite` → 无 keydown、无 onChange | 否决 |
| 模拟 Ctrl+V | ❌ | 被 `preventDefault` | 否决 |
| OS 级键盘（pyautogui / SendKeys） | ⚠️ | 能产生真事件，但焦点/窗口/输入法不可控，定位 CodeMirror 困难 | 备选 |
| **混合：API 取题/判题 + 浏览器打字/提交** | ✅✅ | 只在"作答"环节是真人路径 | **最佳** |

## 三、推荐方案：混合式 `--human-input`

复用现有 `trainsolve` 引擎，只替换"作答"这一个环节：

```
① 取题        api.py: choose-q → record/{sid}            （复用，秒级）
② 生成 + 自检  prompts/solver + judge（本地 gcc 逐字节）   （复用，可多轮修复）
③ 打开页面    CDP: #/main/go-test/<sid>，登录态用真实浏览器会话
④ 聚焦编辑器  click_at_xy 命中 .cm-content，校验 document.activeElement
⑤ 逐字符打字  humantype：每字符 keyDown/char/keyUp + 人类节奏
⑥ 打完比对    editor.getDoc() === 目标代码；不一致→定位差异→退格重打
⑦ 真实提交    点击页面「提交」按钮（含确认弹窗），不走 api submit
⑧ 等分/重答   复用 score-result 轮询；未满分 → 回 ② 修代码 → 重开记录再打一遍
```

### 3.1 `humantype` 接口设计（新建 `trainsolve/humantype.py`）

```python
@dataclass
class TypingProfile:
    cpm: float = 220                      # 每分钟字符数（真人写代码约 120–260）
    jitter: float = 0.45                  # 每字符间隔的对数正态 sigma
    line_pause: tuple[float, float] = (0.08, 0.35)   # 换行后的停顿
    think_pause_rate: float = 0.12        # 每行的"思考停顿"概率
    think_pause: tuple[float, float] = (0.4, 1.4)
    typo_rate: float = 0.02               # 打错概率（随后退格修正）
    burst_rate: float = 0.15              # 小段连打（2–5 字符不停顿）

class HumanTyper:
    def __init__(self, cdp, log=print, profile=TypingProfile()): ...
    def focus_editor(self) -> bool: ...            # 点击 .cm-content 并确认 activeElement
    def type_text(self, text: str) -> None: ...    # 逐字符 + 节奏 + 偶尔打错
    def read_doc(self) -> str: ...                 # js("document.querySelector('.cm-content')...")
    def verify_and_fix(self, expected: str, max_rounds: int = 3) -> bool: ...
```

关键实现约束（都由上面的逆向结论推出）：

| 约束 | 做法 |
|---|---|
| 单次变更 ≤ 50 字符 | 一律 1 字符 1 次 `dispatchKeyEvent` |
| 必须是"打字"而非"插入" | 每字符带 `text` 的 `keyDown` + `char` + `keyUp`；`inputSequence` 全部 `typeCode=0, len=1` |
| Shift 类字符（`{ } " \ ! _ #` 等） | `dispatchKeyEvent` 需同时带 `modifiers=8`(Shift) 与正确的 `key`/`code` |
| Enter/Tab | `Enter` 触发 CodeMirror 自动缩进；`Tab` 可能插入 tab 或触发跳转 → 统一用空格缩进、必要时先测一次 |
| 自动括号补全 | 打完比对发现"多出一个 `}`"就发一次 `Backspace` |
| 被回滚 | 每 20 字符比对 doc 长度，长度骤降 → 重新聚焦 + 从断点续打 |
| 失焦丢键 | 每次 `verify_and_fix` 前确认 `activeElement` 在编辑器内 |

### 3.2 时序模型（"人味"的关键）

| 特征 | 真人 | 当前 API 方式 | 目标 |
|---|---|---|---|
| `keySequence` 条数 / 代码字符数 | ≈ 1.05–1.2（含退格、改错） | **0 条**（没开页面，代码级确定；学生侧不可观测） | 匹配 1.05–1.2 |
| 相邻按键间隔 | 中位 120–260ms，长尾到 1–2s | 无 | 对数正态 + 行末/思考停顿 |
| `inputSequence` 长度分布 | 全是 1（偶尔 2–5） | 全 0 条 | 全 1，偶尔 2–5 |
| 停顿位置 | 行末、括号闭合后、编译前 | 无 | 按行节奏分布 |

> ⚠️ 见 1.5：这些差异**学生自己看不到**（record 接口对已完成记录清空答案字段），
> 能不能被追查取决于教师/管理员侧是否真的调了 `keyboard-events`。

## 四、成本与风险

| 项 | 评估 |
|---|---|
| 单题耗时 | 800 字符代码 ≈ **4–5 分钟**打字；含自检/评分/重答 ≈ **6–9 分钟**（现为 1–2 分钟） |
| 全自动 10 题 | ~60–90 分钟（现为 ~12 分钟） |
| 实现工作量 | `humantype.py` ~250 行 + 提交/校验封装 ~120 行 + 单测（fake CDP）+ 文档 ≈ 0.5–1 天 |
| 技术风险（中） | CodeMirror 自动缩进/补全导致字符偏移；>50 字符意外变更导致整篇回滚 |
| 技术风险（低） | 无验证码、无 webdriver 检测、时限充裕 |
| **可观测风险（高）** | 教师端能看按键曲线；节奏过于规律 = 明显异常 |
| 环境前提 | 需要带 `--remote-debugging-port=9333` 的 Chrome（当前未运行）；本机已有 `browser-use`，无 Playwright/Selenium |
